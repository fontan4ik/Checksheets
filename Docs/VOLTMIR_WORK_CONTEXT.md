# Контекст дальнейшей работы Voltmir

Дата фиксации: 2026-09-14

## Компания и цель

Voltmir развивает API-интеграции и оптимизацию бизнес-процессов для маркетплейсов WB, Ozon и Яндекс Маркета. Рабочая цель проекта Checksheets — обеспечить надёжную синхронизацию каталога, остатков, цен, заказов, рекламы и операционных показателей с Google Sheets без потери ручного управления и без затирания валидных данных ошибочными ответами API.

## Текущее рабочее пространство

Репозиторий: `Checksheets`.

Архитектура гибридная:

- Google Apps Script обслуживает книгу, каталог, текущие цены и остатки, записи по Ozon/WB, формулы и компактные аналитические итоги.
- Локальные Python/Node-процессы выполняют тяжёлые синхронизации поставщиков, Ozon Performance Ads, CPC-операции и отдельные фоновые задачи.
- Google Sheets остаётся оперативным интерфейсом и источником ручных сопоставлений.
- Логи и аудиты используются для расследования фактических отправленных payload, а не только для просмотра итоговых значений.

Основная книга: spreadsheet ID зафиксирован в проектной конфигурации; ключевая рабочая вкладка — `тест`/`ТЕСТ` в зависимости от конкретного потока. Не менять ID, листы, Telegram bindings и ручные поля без отдельного согласования.

## Что уже является важным контуром

1. Ozon: карточки, product ID/SKU, FBO/FBS остатки, цены, заказы/аналитика и Performance Ads.
2. Wildberries: nmId, заказы, аналитика, цены, FBO/FBS остатки и отправка остатков по складам.
3. Поставщики: ETM, Feron, RS, а также отдельные потоки ARL/ODC/gaus и агрегирование для Яндекс Маркета.
4. Huckster: чтение текущих/рекомендуемых цен и отдельная запись минимальной цены из `ARL TR`.
5. CPC Ozon: создание кампаний, аналитика с порогами остановки, ставки и переключение кампаний из листа `СРС`.
6. CDEK/FBS и Telegram: фоновые синхронизации и уведомления о результатах/ошибках.
7. Arlight: отдельный локальный API-поток с lock-обёрткой, LaunchAgent и тестами.
8. Контроль размера Google Sheets: книга близка к лимиту 10 млн ячеек, поэтому подготовлен план поэтапного переноса истории и тяжёлой аналитики в BigQuery.

## Ближайший согласованный вектор

Работать поэтапно, не ломая текущий production-контур:

1. Сначала измерить и безопасно сократить созданную сетку книги после резервной копии; удалять только согласованные хвостовые строки/столбцы.
2. Зафиксировать реестр потоков, диапазонов, периодов, естественных ключей, SLA и baseline минимум за несколько запусков.
3. Подготовить BigQuery dataset, схемы `sync_runs`, `data_quality_results`, `dim_product`, `dim_warehouse` и фактов.
4. Первым пилотом выбрать Ozon-рекламу: локальный сборщик → dual-write → сверка по SKU и суммам → shadow read → controlled cutover.
5. Затем переносить дневные факты заказов Ozon/WB, после этого — историю цен и остатков.
6. После подтверждённых сверок физически убирать историю из Sheets и оставлять в книге только текущие значения и компактные итоги.

Подробный проектный план находится в `Docs/BIGQUERY_MIGRATION_PLAN.md`; его статус — планирование, миграция ещё не считается выполненной.

## Непересекаемые правила разработки

- Не редактировать Apps Script только в браузере: сначала менять локальный файл, затем загружать согласованный файл.
- Не трогать ручные формулы и управляющие поля, особенно колонку B и ручные поля цен/фильтров.
- Для Ozon product ID отбрасывать пустые, нулевые и нечисловые значения.
- Соблюдать лимиты API: Ozon Seller около 20 RPS в общем контуре, Ozon Analytics около одного запроса в 7 секунд, WB около 2 RPS.
- Локальные сетевые скрипты должны использовать предусмотренный `SourceAddressAdapter`/VPN guard; не возвращать несовместимый source-address-only bind для Network Extension VPN.
- Каждый локальный WB stock writer обязан использовать `wb_stock_audit.js`.
- Для StreamSupps сохранять правило: `AB = N + S + V → WB 798761 (ВольтМир)`; `AC = M + X → WB 1449484 (ФБС ФЕРОН МОСКВА)`. M включает Feron Moscow и Arlight из `ARL TR`, X добавляет «РУССКИЙ СВЕТ МОСКВА». Единственный регулярный writer склада 1449484 — `sync-feron-stocks.js`, который читает AC.
- Не затирать последнее валидное значение нулём при ошибке API, пустом ответе или устаревшем снимке.
- Для BigQuery использовать staging + `MERGE`, строковые идентификаторы, `NUMERIC` для денег, UTC timestamps и явные бизнес-периоды.
- Все новые документы размещать в `Docs/`, тесты и диагностику — в `test/`; секреты не читать и не добавлять в документацию.
- Не коммитить, не отправлять изменения и не менять историю Git без прямого запроса.

## Проверка перед завершением задачи

1. Уточнить затронутые файлы и текущий `git status`.
2. Найти определения и usages изменяемых функций до правки.
3. Выполнить минимальные релевантные тесты/линтер или безопасную проверку синтаксиса.
4. Для потоков записи сверить диапазон, число строк, checksum и audit.
5. Для Apps Script подготовить инструкцию загрузки и имя функции для контрольного запуска в IDE.
6. В Paperclip оставить краткий комментарий с результатом, проверкой и оставшимися решениями.

## Открытые решения, которые нельзя принимать молча

- Google Cloud project, billing account и регион BigQuery.
- Точная политика хранения raw/staging и снимков цен/остатков.
- Допустимые SLA и пороги сверки для каждого потока.
- Какие вкладки и исторические диапазоны можно вынести после резервной копии.
- Когда бизнес готов переключить конкретный поток из Sheets-only в dual-write и далее в BigQuery-primary.

## Формат следующей работы

Каждую следующую задачу вести как небольшой проверяемый инкремент: контекст → минимальная правка → локальная проверка → фактический результат в комментарии. При неопределённости по бизнес-смыслу периода, колонке или целевому листу сначала предложить вариант пользователю, а не менять поведение молча.
