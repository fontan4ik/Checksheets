# Актуализация CODES в StreamSupps

## Назначение

С 16.10.2026 `sync_etm_codes.py` снова заполняет только пустые `CODES` в StreamSupps по FTP-выгрузкам `price.csv` из `/from_etm/13` и `/from_etm/14`. Существующие коды сохраняются; неоднозначные совпадения пропускаются. Перед записью каждого источника лист перечитывается. Для диагностики без записи используется `--dry-run`.

## Сопоставление и приоритет

1. Бренд берётся из колонки **D** (`brand`).
2. Сначала проверяется пара `model + brand` (модель из **B**) по складу 13.
3. Затем для оставшихся пустых `CODES` проверяется пара `art + brand` (артикул из **A**) по складу 13.
4. После этого только оставшиеся пустые `CODES` проходят те же проверки по складу 14.
5. Любое уже непустое значение в `CODES` не изменяется, даже если код отличается от FTP.
6. Если модель и артикул дают разные коды, строка пропускается как неоднозначная.
7. Несовпавшие строки не очищаются.

Колонки разрешаются по заголовкам. Документированное исключение только для чтения: в текущем StreamSupps ключевой артикул находится в A с пустым заголовком; при непустом неизвестном заголовке скрипт останавливается. Целевая колонка всегда определяется строго по `CODES`.

Источник ETM: `Код ЭТМ`, `Артикул`, `Производитель`; поддерживается кодировка CP1251.

## Надёжность FTP-загрузки

- Timeout FTP-подключения и передачи по умолчанию — **300 секунд** (`ETM_FTP_TIMEOUT`).
- Каждый файл скачивается максимум за **3 полные попытки** (`ETM_FTP_DOWNLOAD_ATTEMPTS`).
- Перед каждой повторной попыткой создаётся новое FTP-соединение; backoff — **2, 4 секунды** (`ETM_FTP_DOWNLOAD_BASE_DELAY`).
- Файл собирается в памяти и попадает в локальный кеш только после полного завершения `RETR` и strict-проверки всего CSV: кодировка, ожидаемый заголовок и наличие строк данных.
- Кеш заменяется атомарно; неполная или повреждённая передача не может заменить последний полный файл.
- В логах отдельно фиксируются путь, номер попытки, полученные байты, длительность передачи, результат CSV-проверки и причина ошибки.
- Каждый запуск повторно проверяет пустые коды даже при неизменном FTP-файле: на листе могли появиться новые товары.
- Если склад недоступен, его источник не считается обработанным; существующие значения в `CODES` не очищаются и не перезаписываются.

## Запуск диагностики

```bash
# Только расчёт по складам 13 -> 14, без записи
./.venv-etm-export/bin/python sync_etm_codes.py --dry-run

# Проверка на локальном файле (один источник)
./.venv-etm-export/bin/python sync_etm_codes.py --dry-run --csv test/tmp/etm_ftp_downloads/from_etm/13/price.csv
```

Файл состояния: `test/tmp/etm_codes_ftp_state.json`. Логи: `logs/sync_etm_codes.log` и `logs/sync_etm_codes_launchd.log`.

## Расписание

LaunchAgent `com.voltmir.checksheets-etm-codes` ежедневно в 08:30 Asia/Dubai запускает запись через `run_with_lock.sh sync_etm_codes` и `.venv-etm-export/bin/python`. Существующая защита от параллельного запуска и уведомления Telegram сохраняются.

## Проверенные соответствия вне точного FTP-сопоставления

После FTP 13 → 14 применяется `etm_code_verified_matches.json`: подтверждённые по полному API/каталогу ЭТМ и идентичности товара соответствия для конкретных артикулов продавца. Требуется точное совпадение модели и ожидаемого бренда; ранее заполненный CODES не изменяется. Неоднозначный или повреждённый реестр отклоняется до записи. Режим `--verified-only` пропускает FTP, `--dry-run` исключает запись.

Итог дополнительного разбора 338 пропусков: 312 позиций теперь с кодами, 26 остаются пустыми (17 реальных товаров без однозначного подтверждения и 9 тестовых строк). Проверено 21 971 заполненный CODES из 21 997, 0 изменений существующих кодов, 0 расхождений с реестром. Подробности и список остатка: `Docs/etm_codes_identity_resolution_20261016.md`.
