# План исправления подтверждённых сбоев

Основа: 150 записей `logs/script_errors.jsonl` за 29 сентября — 1 октября 2026 года. Количество записей показывает частоту уведомлений, а не число независимых причин. Telegram bot token и chat binding остаются прежними.

## 1. Ozon Performance: HTTP 403 на статистике SKU (78 записей)

**Причина для проверки:** запрос `POST /api/client/statistics/products/sku` получает `Ошибка авторизации, ресурс недоступен`. Скрипт `ozon_cpc_cleanup.py` завершает работу; отсутствие новых строк кампаний не делает запуск успешным.

1. Сверить текущий аккаунт, права и доступ к этому методу с теми же реквизитами, которые успешно вызывают другие методы Performance API. Не выводить токены в логи.
2. Разделить случаи «токен недействителен», «нет права на ресурс» и «метод/версия недоступны» по фактическому ответу API; исправить только установленную причину.
3. Выполнить один ограниченный запрос статистики и затем один штатный запуск. Успех: HTTP 403 исчез, нужные данные записаны, повторный запуск не создаёт новый инцидент.

## 2. Остатки Ozon/WB: неустранённые ошибки и расхождения (13 записей)

**Масштаб по отчётам:** 8 уведомлений о записи Ozon (2 264 товарные операции с ошибкой), 3 post-check WB (53 расхождения), 2 ошибки записи отдельных товаров WB. Это частично завершённые синхронизации.

1. По каждому запуску связать `runId`, склад, код ошибки, артикул и исходный снимок. Для WB опираться на `logs/wb_stock_payload_audit_*.jsonl`, в том числе checksum подготовленного батча и результаты индивидуального fallback после HTTP 409.
2. Отделить причины записи Ozon от причин WB post-check. Проверить снимки старше 15 минут: повторное использование старых значений может давать расхождение даже после корректного запроса.
3. Исправить подтверждённые причины в соответствующих ETM/Feron/RS writer без изменения складских маршрутов и обязательного WB payload audit. Повторить только затронутые операции, затем сверить фактические остатки.
4. Успех: `errorSku=0`, post-check без расхождений для затронутых складов; предупреждения о старом снимке остаются видимыми.

## 3. Связь с GitHub и Google (28 + 19 записей)

**GitHub:** 21 `SSL_ERROR_SYSCALL` и 7 ошибок соединения при `git fetch`. **Google:** 17 прямых сбоев OAuth/Sheets и 2 остановки ETM, где сообщение о «нестабильности» скрывает неудачные чтения таблицы.

1. Во время следующего инцидента зафиксировать маршрут, DNS и доступность `github.com`, `oauth2.googleapis.com`, `sheets.googleapis.com` через используемый сетевой интерфейс. Проверить влияние VPN и текущих настроек привязки интерфейса отдельно для Python и Node.
2. Для ETM сообщать о последней ошибке чтения как о причине остановки. После восстановления соединения запускать полный цикл чтения нового снимка, не продолжать со старым.
3. Для GitHub сначала подтвердить `fetch`, затем состояние ветки и только после этого штатный цикл watcher. Координировать его lock/state с `clasp push`.
4. Успех: Google OAuth/Sheets читаются, ETM завершает обновление, `git fetch` и watcher завершаются успешно. Повторы одного сетевого инцидента объединяются в одно Telegram-уведомление с сообщением о восстановлении.

## 4. Отчёт хранения Ozon: заголовок не распознан (1 запись)

1. Сохранить обезличенный образец строки заголовков в `test/` и сравнить с вариантами, которые ищет `storageMapFromRows()` в `ozon_report65_local.js`.
2. Добавить подтверждённый вариант заголовка и проверить разбор суммы и ключа товара на образце.
3. Успех: штатный отчёт разбирается, итоговые суммы сверяются с исходным файлом, обновление листа завершается без ошибки.

## 5. Повторяемые ограничения API и изменение каталога (3 + 2 записи)

1. Для Ozon HTTP 429 проверить частоту и перекрытие запусков Buyout/CPC; соблюдать `Retry-After`, повторять с задержкой и ограничить конкуренцию запросов.
2. Для RS при изменении пагинации начинать чтение категории заново с первой страницы. Ограничить число полных повторов и сохранять защиту от неполного снимка.
3. Успех: временное ограничение проходит после повторов; если обязательное обновление не состоялось, событие поднимается до ERROR с исходной причиной.

## Порядок выполнения

Сначала пункты 1 и 2: они блокируют рекламную аналитику и оставляют неподтверждённые остатки. Затем пункт 3, поскольку общая проблема сети затрагивает несколько сервисов. После восстановления связности — пункт 4 и настройки повторов из пункта 5.
