# План устранения подтверждённых ошибок

Срез: 232 записи в `logs/script_errors.jsonl` за 29 сентября — 1 октября 2026 года (последняя запись на момент анализа — 1 октября, 21:09 +04:00). Лог продолжает пополняться, поэтому число уведомлений не равно числу независимых причин. Telegram token и chat binding не менялись.

## Исправлено в локальном коде

- Ответы Ozon `PRODUCT_IS_ARCHIVED`, `NOT_FOUND_ERROR`, `NOT_PASS_MODERATION` и `PRODUCT_IS_NOT_CREATED` для стоковых писателей учитываются как терминальные пропуски; они не раздувают ошибки записи и post-check.
- Перед записью остатков WB ETM и Feron перечитывают Google Sheet после Ozon этапа. Обязательный `wb_stock_audit.js` и предупреждения `WB STALE SNAPSHOT` сохранены.
- RS при изменении пагинации отбрасывает частичный снимок и повторяет чтение категории с первой страницы, максимум три попытки.
- CPC status GET повторяется на HTTP 429/временных ошибках с backoff; Ozon Buyout в `Shared_HTTP.js` теперь учитывает `Retry-After` в пределах бюджета ожидания 90 секунд и отдаёт финальный ответ вызывающему коду, если сервер просит ждать дольше.
- Если заголовок выгрузки Report65 не распознан, скрипт один раз заново генерирует отчёт. До успешного разбора данные в лист не записываются.
- Изменения исходников во время GitHub sync откладывают цикл без ERROR; сетевой сбой при `git fetch` по-прежнему остаётся ERROR.

## Оставшиеся реальные проблемы

### 1. Ozon Performance: HTTP 403 на статистике SKU

Повторяемый `POST /api/client/statistics/products/sku` получает `Ошибка авторизации, ресурс недоступен`. Это не исправляется retry-логикой: нужно сверить аккаунт, право на endpoint и доступность метода/версии с теми же реквизитами. Токены в диагностику и логи не выводить. Успех — ограниченный запрос и следующий штатный запуск завершаются без 403 и записывают данные.

### 2. Ограничения товара и остатки

- `OVER_MAX_OVH_NON_KGT` остаётся настоящим отказом Ozon: нужно сверить допустимый остаток и тип товара по артикулам. Ошибку не подавлять и складские маршруты без подтверждения не менять.
- Исторические WB post-check расхождения нужно перепроверить после развёртывания свежего чтения снимка. Аудит сверять по `runId`, batch checksum и `offerId`/`chrtId`; предупреждения о снимке старше 15 минут оставлять видимыми.
- Проверить результаты следующего успешного запуска: `errorSku`, остатки Ozon/WB и записи `logs/wb_stock_payload_audit_*.jsonl`. Кодовые изменения сами по себе не исправляют остатки, уже отклонённые API.

### 3. GitHub и Google connectivity

`git fetch`, Google OAuth и Sheets имеют ошибки DNS, маршрута/соединения и TLS в соседних скриптах. Это внешняя проблема хоста/сети, не ошибка бизнес-логики. При следующем инциденте проверить DNS/маршрут до `github.com`, `oauth2.googleapis.com` и `sheets.googleapis.com` через текущий VPN/интерфейс. Сетевые сбои оставлять ошибками; повторять полную загрузку свежего снимка после восстановления связи.

### 4. Верификация оставшихся исправлений

Автосинхронизация уже отправила `Shared_HTTP.js` в bound Apps Script и подтвердила совпадение 46 tracked файлов после pull. Следующие штатные запуски покажут, сработали ли новый `Retry-After`, повтор Report65 и свежий WB снимок. Для любого остатка выше порогов открыть аудит конкретного `runId`; не выполнять массовую повторную запись вслепую.
