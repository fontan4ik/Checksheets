ПРОВЕРЕННЫЙ СПОСОБ ЗАГРУЗКИ PDF НА OZON

POST /v2/product/certificate/create

Фактически сработавшая структура для декларации Navigator 14048-1:

{
  "params": {
    "name": "Декларация о соответствии № ЕАЭС N RU Д-CN.РА07.В.18481/22",
    "certificate_type": "DECLARATION",
    "certificate_country": "RU",
    "accordance_type": "EAEU",
    "number": "ЕАЭС N RU Д-CN.РА07.В.18481/22",
    "issue_date": "2022-10-07T00:00:00Z",
    "expired_date": {"date": {"day": 5, "month": 10, "year": 2027}},
    "skus": ["5523523330"],
    "product_type": "UNKNOWN",
    "files": [{"file_content": "BASE64_ИСХОДНОГО_PDF", "name": "NAV_declaration_14048_bb50bd4efe46.pdf"}],
    "link_to_registry": "https://pub.fsa.gov.ru/rds/declaration/view/17092904"
  }
}

file_content создавай base64.b64encode(path.read_bytes()).decode('ascii'), без префикса data:. Перед отправкой проверь SHA-256. Скан и приложения должны составлять полный документ. Не подменяй оригинал выпиской реестра или PDF другого документа.

Оба новых запроса вернули certificate_id, status="COMPLETED", все params[].state="VALID". Затем независимым чтением подтверждены status_code="approved" и product_status_code="approved" для нужных товаров. COMPLETED сам по себе ещё не является окончательным одобрением.

Для сертификата соответствия исторически использовался CERTIFICATE_OF_CONFORMITY, но в текущем запуске новый сертификат этого типа не создавался. Не переносить автоматически lowercase значения справочника v1 в поле certificate_type v2: версии имеют разные формы контракта.

Размер JSON учитывает увеличение файла примерно на треть из-за base64. В прошлой работе от 6 октября сервер отклонял большие запросы с сообщением grpc max 15728640, иногда HTTP429. Не путай это с обычным ограничением частоты: смотри тело ответа. Современный точный максимальный размер здесь отдельно не проверялся; испытанные PDF — 810483 и 430100 байт. Для больших файлов уточни допустимый способ у Ozon, не изменяй оригинал молча.

ПРОВЕРЕННЫЙ СПОСОБ ПРИКРЕПЛЕНИЯ ДОКУМЕНТОВ НА WB

POST /content/v2/cards/update
Тело — массив карточек. Три карточки и четыре документа реально приняты: error=false; независимое чтение вернуло новые документы с серверными id.

Здесь передаются реестровые сведения о документе. Поля загрузки PDF, URL файла или его байтов в прочитанной схеме documents нет. Поэтому результат WB называй «документ прикреплён в карточке», а не «PDF загружен».

Пример новой записи documents:

"documents": {
  "items": [{
    "type": 2,
    "number": "ЕАЭС N RU Д-CN.РА07.В.18481/22",
    "startDate": "2022-10-07T00:00:00Z",
    "endDate": "2027-10-05T00:00:00Z",
    "isEndless": false
  }],
  "excludeDocuments": false
}

Для нового документа id не передавай. У существующего сохраняй id и остальные исходные разрешённые поля. Не отправляй серверные verdict/createdAt. Тип1 — сертификат, тип2 — декларация. Дополнительные поля схемы: productNumber, tradeName, applicant; не придумывай их значения.

Карточка и documents перезаписываются целиком. Испытанный payload копирует из свежего чтения nmID, vendorCode, brand, title, description, dimensions, characteristics, sizes, kizMarked и gtin при наличии. Все прежние размеры, баркоды и документы сохраняются. photos/video/tags этим методом не изменяются, но их сохранность проверена чтением. kizMarked сохраняй обязательно.

Никогда не отправляй только nmID+documents и не заменяй исходный список документов одним новым. excludeDocuments=true не является способом исправить ошибку загрузки: это отдельное утверждение о ненужности документов и стирание их значений.

Документированные ограничения WB: до 3000 карточек / 10 МБ, 10 запросов/минуту, интервал 6 секунд, burst 5. Проверка может идти до 3 дней; повторная запись запускает её заново. Перед масштабированием перечитай текущие ограничения по официальной ссылке выше. Испытание содержало один запрос записи с 3 карточками.

Чтение WB: POST /content/v2/get/cards/list
Тело:
{"settings":{"sort":{"ascending":true},"cursor":{"limit":100},"filter":{"withPhoto":-1,"textSearch":"14048-1"}}}

textSearch — поиск, не доказательство точного соответствия. После ответа оставляй только карточки с точным vendorCode. Проверенный helper читает все страницы даже при фильтре. Для полного каталога убери textSearch. В следующий cursor переноси updatedAt и nmID из ответа; конец при cursor.total<limit. Повтор курсора, несовпадение total/числа карточек или ошибка запроса означают неполную проверку.

Архивные карточки/корзину учитывай отдельно через документированный метод списка корзины; он в этом запуске не испытывался. Для разбора отказов смотри /content/v2/cards/error/list по его актуальной официальной схеме; отдельная проверка этого метода здесь не проводилась.

ОКОНЧАТЕЛЬНОЕ ПОДТВЕРЖДЕНИЕ WB

Точное совпадение товара, полного номера, типа и дат. documents.excludeDocuments=false. Нужный item.verdict.verified=true и item.verdict.status=1. Отсутствие verdict не является успехом. Не требуй reason="valid": официальная схема допускает reason=null при успехе; отказ имеет status2.

Для проведённой очистки дополнительно требуется overallVerdict.isFullyChecked=true и overallVerdict.status=1. Один общий положительный вердикт не заменяет положительный вердикт КОНКРЕТНОГО документа. После записи общий вердикт может ещё содержать старые дату и результат — сравнивай временные отметки, не принимай старое состояние за завершение новой проверки.

WB меняет порядок characteristics между одинаковыми чтениями. Сравнивай характеристики по id, сохраняя значения; перестановка не является изменением товара. В реальном испытании WB также добавил связанные с документами характеристики 15001135,15001137,15001138 — номер декларации и даты. Все прежние характеристики и прочие поля сохранены. Не игнорируй любые другие изменения под видом перестановки.

ПОРЯДОК РАБОТЫ ДЛЯ ВСЕХ ТОВАРОВ

1. Полностью выгрузи текущие каталоги обеих площадок и исходную таблицу. Объедини товары, сохраняя точные артикулы и ведущие нули; не пропускай отсутствующие на одной площадке. Построй offer_id/product_id/SKU ↔ vendorCode/все nmID. Дубли, архив и неоднозначности явно пометь.

2. Построй матрицу «товар—каждый необходимый документ». Отдельно учитывай сертификаты, декларации, приложения и документально обоснованные случаи, когда документ не нужен. Отсутствие найденного документа не означает отсутствие требования. Отказное письмо не подменяет обязательный сертификат.

3. Проверь локальные файлы, официальные карточки производителя/поставщика и реестры. Для каждого документа запиши полный номер, тип, страну, даты, производителя, источник, точную область применения, путь, SHA и все товары. Просматривай основной документ и приложения. OCR — средство поиска; исправлять символы можно только после чтения оригинала. Номер из имени файла или наличие у товара другого принятого сертификата не доказывает идентичность этого PDF.

4. Нормализуй только формат: пробелы, пунктуацию, представление префикса и однозначные визуальные варианты латиницы/кириллицы. Сохраняй страну, год, тип и все значимые части номера. Не используй совпадение последних цифр, «похожий бренд» или автоматическое исправление8→В.

5. Найди существующие записи на площадках. Принятую запись используй повторно, добавляя лишь недостающие доказанные привязки. Не создавай дубли отклонённых или ожидающих документов. Если исходный документ и карточка расходятся, сначала объясни расхождение.

6. Выполни маленькую партию; сохрани снимки и план до первой записи. На WB копируй свежую карточку полностью. При содержательном конкурентном изменении пересобери план. Логи изменений должны позволять продолжить после остановки без повторной загрузки.

7. После записи независимо перечитай серверное состояние. Транспортная ошибка записи/тайм-аут/5xx означает неопределённый результат. Сначала ищи запись по полному номеру и проверяй привязки; не повторяй create/update автоматически. Клиент этого запуска автоматически повторяет только чтения. Отложенные проверки вынеси в очередь со временем проверки; продолжай остальные независимые товары.

8. Перед очисткой заново проверь все привязки данного файла на обеих площадках. Общий документ нельзя убрать, если хотя бы одному нужному товару он ещё не применён. Отсутствие карточки блокирует очистку; создание карточек требует отдельной задачи. Проверка должна охватывать все известные связи по файлу/номеру, все копии, новые сопоставления и дополнительные модели текущего каталога, подпадающие под документ. Старый local_map — исходный материал, а не вечная гарантия полноты.

9. Сформируй allowlist файлов: абсолютный путь, точный SHA, размер, документы, все товарные ID, положительные статусы, время и доказательство применимости. Папки с реестрами/Excel/CSV/JSON/журналами не удаляй. Перечитай hash всех файлов до первого перемещения и непосредственно перед каждым. Запиши prepared с source/trash_path/SHA, затем перемести в отдельную папку корзины, перечитай target SHA и запиши verified_moved. Не очищай корзину автоматически.

10. Сдай покрытие всех товаров, список загруженного, подтверждённого на одной/обеих площадках, ожиданий, отказов и нерешённых моделей. Разделяй число уникальных документов, товаров, связей и файлов. Сохраняй причины отказов и точный способ продолжения. Не объявляй «все товары закрыты», если остаются пропуски.
