# Автодобавление артикулов

Выбор пользователя 2026-10-15: полный каталог Ozon из API, а для UNIT WB —
артикулы продавца из API WB. В колонку A добавляются только отсутствующие позиции.

## Рабочая реализация

- `catalog_articles_local.js`: локальный Node.js процесс.
- `scripts/com.checksheets.catalog-articles.plist`: LaunchAgent раз в 3600 секунд.
- Установлен в `~/Library/LaunchAgents/com.checksheets.catalog-articles.plist`,
  label `com.checksheets.catalog-articles`.
- Ручной запуск: `node catalog_articles_local.js`; предварительная сверка без записи:
  `node catalog_articles_local.js --dry-run`.
- Требуется включённый Mac и сеть; после сна LaunchAgent продолжает штатную работу.

| Источник | Листы |
|---|---|
| Ozon `/v3/product/list`, visibility ALL, точный offer_id | ТЗ, ОБОР, Дизайн контент, StreamSupps |
| WB Content `/content/v2/get/cards/list`, vendorCode, withPhoto -1 | UNIT WB |

Корзина удалённых карточек WB не включается. Суффиксы комплектов (`-1`, `-5`,
`-10`) не удаляются. В ОБОР добавляются точные offer_id, даже если уже есть
базовый артикул производителя.

Колонки разрешаются по заголовкам с проверкой уникальности и расположения в A.
Единственное исключение: у Дизайн контент A1 пустая, проверено 2026-10-15.
При изменении схемы соответствующий лист не записывается, ошибка отправляется
через существующий Telegram notifier. Токен и канал Telegram не менялись.

Сверка по видимому тексту артикула (FORMATTED_VALUE): в UNIT WB встречаются
числовые значения с пользовательским форматом, отображающим артикул продавца.
Ведущие нули и регистр сохраняются; удаляются только пробелы по краям.
Повторные артикулы API исключаются, существующие дубли не удаляются.

Сначала полностью загружается каталог площадки, затем непосредственно перед
записью заново читается A целевого листа. Запись идёт после последнего значения
или формулы в A; пустая формула тоже занимает строку. Пропуски внутри не
заполняются, существующие строки и колонки B и далее не переписываются.
Добавление физических строк и запись `userEnteredValue.stringValue` выполняются
атомарным Sheets batchUpdate. После записи читается и сравнивается весь блок A.

Обрабатывается только один локальный запуск. После потери ответа на запись
запрос не отправляется повторно: следующий проход сначала перечитает A, поэтому
уже записанные позиции не добавятся дважды. Чтение/API запросы имеют ограниченные
повторы на временные ошибки. При сбое одного листа остальные проверяются.

## Журналы и проверка

- `logs/catalog-articles-last.json`: источники, добавленные диапазоны, ошибки.
- `logs/catalog-articles-pending.json`: подготовленный блок до подтверждения записи.
- `logs/catalog-articles-launchd.log`, `.err`: вывод запланированных запусков.
- `node test/test_catalog_articles_local.js`: заголовки, пустые формулы, суффиксы,
  ведущие нули, атомарная запись только A и восстановление после потери ответа.
- `test/verify_catalog_articles_live.py`: независимая проверка живых листов.

## Почему локально

Проверенный прототип Apps Script лежит в `test/catalog_articles_gas_prototype.js`
и не загружается в облако. В проекте занят лимит триггеров, общий ScriptLock часто
занят аналитикой, обычный SpreadsheetApp задержал первую страницу на 4 минуты.
Даже после перехода к Sheets API запрос страницы WB из Google занимал около
10 секунд против примерно 1–2 секунд локально. Локальный процесс не ограничен
шестью минутами одного выполнения и загружает полный каталог за один проход.

Созданный при проверке Google-диспетчер отключён; исходный legacy-триггер
`updateOzonReviewCountBL` восстановлен (ежедневно 15–16 по Asia/Dubai).
Прототип убран из рабочего облачного проекта, manifest возвращён к исходному
составу сервисов. Google Sheets API в Cloud-проекте 175784251448 был включён только при
проверке прототипа и возвращён в исходное состояние DISABLED; новые ключи не создавались. Локальный Node исключён в `.claspignore`.
