# Автономный расчёт НТЦ

Этот модуль остался отдельным исследовательским прототипом. Для первого этапа с прямым изменением F используется `ntc_f_stage.py`: он не записывает и не рассчитывает L, поскольку L уже является формулой в таблице. См. «НТЦ — полный алгоритм и первый этап с F.md».

`ntc_stock_engine.py` — локальный модуль без доступа к Google Sheets, Ozon или маркетплейсам. Он читает локальный JSON, считает потенциальные значения колонки L и печатает результат. Ничего не записывает.

```bash
.venv-etm-export/bin/python ntc_stock_engine.py --input test/ntc_stock_example.json
.venv-etm-export/bin/python test/test_ntc_stock_engine.py -v
```

## Входные данные

- `stock_by_model`: текущие фактические физические остатки F по модели.
- `articles`: соответствие артикула модели и кратности H.
- `postings`: текущий статус отправления, позиции в продаваемых единицах и **исторический** признак `ever_handed_over`. После передачи Ozon этот признак остаётся `true`, даже если статус стал `cancelled`. Если история неизвестна, отменённый заказ остаётся в резерве.
- `outbound_booked`: количество продаваемых единиц конкретного отправления и артикула, которое складская система уже вычла из F. После такого подтверждения отдельный резерв снимается: F уже уменьшен.
- `manual_k`: накопленное ручное списание в продаваемых единицах. `manual_booked`: сколько из него складская система уже вычла из F.
- `returns`: сырые записи возвратов Ozon. Принятым считается только FBS с `visual.status.sys_name = ReceivedBySeller`; ключи — ID возврата, исходный `posting_number`, `product.offer_id` и `product.quantity`. Повтор одного ID игнорируется.
- `return_reconciled`: количество принятого возврата, которое подтверждено складом как доступное в F, **если исходное выбытие ещё не было отражено в F**. Без этого подтверждения статус Ozon сам по себе не освобождает резерв. Если выбытие уже учтено в F, возврат отражается только следующим фактическим значением F; дополнительного прибавления нет.

Подтверждения `outbound_booked`, `manual_booked` и `return_reconciled` являются входными данными будущей интеграции. Их нельзя выводить только из изменения общего числа F: оно могло измениться из-за другого заказа или поступления.

## Выходные данные

- `L_by_offer`: продаваемые единицы для будущей колонки L. Заказ и K снижают именно свой артикул. Дополнительная проверка ограничивает сумму `L × H` фактическим F за вычетом ещё не отражённых операций.
- `unreflected_units_by_offer` и `unreflected_physical_by_model`: сколько пока удерживается поверх F.
- `accepted_return_waiting_for_warehouse_by_offer`: Ozon уже показывает приёмку, но складское подтверждение ещё не поступило.
- `overdrawn_physical_by_model`: удержание больше F; L становится нулём по мере необходимости.

Это прототип расчёта. Он пока не меняет существующие формулы L/M/N и не отправляет остатки на маркетплейсы. Перед подключением нужен источник складских подтверждений по конкретному отправлению/артикулу; без него безопасный резерв может занижать доступный остаток.
