# Облачный склад НТЦ

Целевая книга: https://docs.google.com/spreadsheets/d/1i35SfWZljNR63GEkPuwgU2zVSU_Y2CWoxcRK-LcpjUo/edit
Владелец и исполнитель расписаний: vladimir.romanovich.grebennikov@gmail.com.
Исходники отдельного связанного Apps Script проекта: `ntc-cloud/`. Корневой `.claspignore` исключает всю папку из основного проекта.

## Рабочий интерфейс

Второй видимый лист `Склад НТЦ` содержит модели, физический остаток, поля поставки/списания и пять изображений с назначенными функциями:

- `ntcSupply`: записать поставки из C в физических штуках.
- `ntcWriteOff`: списать количества из D в физических штуках.
- `ntcOpenScanner`: открыть поиск, аппаратный сканер с Enter, очередь, камеру при наличии BarcodeDetector и кнопки поставки/списания.

Успешная операция очищает только обработанные поля. История операций доступна на листе `История склада`. Один UUID сканера соответствует одному неизменному запросу. Повтор после сетевого сбоя использует тот же UUID. Недостаточный физический запас отклоняет всю ручную операцию.

`Штрихкоды`: код, модель, название. Неоднозначные коды отклоняются интерфейсом. Поддерживаются целые физические количества и команды `QTY-3`, `QTY:3`, `X3`, `КОЛ-3`. Первый маркер умножает последнюю порцию; следующие добавляют указанное число. Реальный каталог/произвольные штрихкоды количества старого Grocy пока не мигрированы: доступный checkout содержит код, но не рабочую БД Windows.

## Остатки и заказы

Все назначения определяются по уникальным заголовкам. Текущая схема: F физический общий остаток модели, H кратность, I `Округлённое+прогруз на мп`, J chrlid, K накопленное ручное списание упаковок. Старое ручное K сохраняет историческую семантику, а кнопки C/D работают в физических штуках. Не вводить одну операцию одновременно в K и D.

НТЦ использует журнал `ntc_f_stage.py`: заказ на сборку списывает количество × кратность; отмена до передачи восстанавливает запас; переданная отмена сохраняет списание. Ozon возврат восстанавливает только фактически принятую часть (`ReceivedBySeller`). Неизвестная история отмены сохраняет резерв. Возврат WB не увеличивает физический запас автоматически: после подтверждённого приёма его проводят кнопкой поставки. Распределение J соответствует прежнему алгоритму полного цикла кратностей; суммарные упаковки каждой модели не превышают её физический запас.

Начальная миграция импортирует исторический журнал, включая два уже списанных отправления, дату начала и курсор. Она сверяет все физические запасы до импорта. Существующие заказы не списываются повторно. В исходной и новой книге сейчас 21 артикул и семь моделей; физические запасы совпадают.

F, производные остатки, история движения, очистка пользовательского ввода и журнал сохраняются одним Sheets batchUpdate. После этого публикация абсолютных J идёт в Ozon и WB. Подтверждения записываются по товарам; частичный API сбой повторяет неподтверждённые позиции. Скрытый `_НТЦ MP аудит` хранит подготовленные payloads, checksum, склад, время снимка, исходную колонку, результат и WB 409 разбиения. Неизменившиеся остатки повторно не пишутся.

Google Sheets API не предоставляет compare-and-swap для пользовательских правок. Перед записью проверяются повторно F, L, состав каталога/привязки, модель и количество в очищаемых ячейках; ручное изменение F вне журнала приводит к остановке для сверки. Изменять физические остатки следует через кнопки.

Публикация одного физического пула на обе площадки имеет задержку фонового опроса; гарантии атомарного резервирования между двумя площадками нет.

## Установка и проверки

`ntcInstall()` исполняется в IDE от владельца. Она исправляет скопированные формулы, ссылающиеся на отсутствующие TXOZ/WB листы, заполняет фотографии/SKU/chrtId/кратности из основного каталога и API, оформляет второй лист и импортирует журнал. Она не отправляет остатки на маркетплейсы.

`ntcEnableCloud()` после успешной сверки включает облачное расписание каждые 10 минут заказов/остатков и ежедневный каталог. Локальные LaunchAgent/cron не требуются. Привязки Telegram сохраняются в Script Properties; сообщения отправляются только при реальных сбоях, продолжающиеся ошибки публикации не создают поток одинаковых уведомлений.

Ozon склад подтверждён read-only API: `НТЦ СКЛАД`, ID `1020005000454993`. По решению пользователя используется WB `798761 ВольтМир`, с отдельным владением остатками 21 артикула в новой книге. `798761 ВольтМир` занят главным StreamSupps writer, `1449484 ФБС ФЕРОН МОСКВА` — sync-feron-stocks.js; В прежних ETM/Feron/RS writers и ручных обнулениях эти 21 артикул исключены именно для 798761; остальные товары и склады не изменены. Перед завершением установки `NTC_LIVE=false`. Кнопки `ntcToggleOzon` / `ntcToggleWb` на втором листе независимо включают/выключают только передачу остатков. Учёт заказов продолжается.

Локальные проверки:

```sh
node test/test_ntc_cloud_engine.js
node test/test_ntc_cloud_marketplaces.js
node test/test_ntc_cloud_flow.js
```

Перед clasp push: проверить отдельные `.clasp.json`/`.claspignore`/status, снять резервную копию удалённого проекта в `test/`, убедиться parentId соответствует новой книге. После push: pull в `test/` и сравнить все исходники. Запуск IDE, журнал Executions и readback новых ячеек обязательны; mock-тесты не являются доказательством работы облака.

1. На «НТЦ списания» добавьте артикул продавца в A, например `55189-20`. Суффикс — физическая кратность упаковки. Для артикула другого формата явно укажите модель B и кратность H.
2. На «Склад НТЦ» нажмите шестую кнопку «Прогрузить данные о товарах». Она заполняет отсутствующие фото, SKU Ozon, nmId WB, chrtId из основного проекта с API fallback; регистрирует модель в журнале и обновляет список моделей. Уже заполненные поля и формулы не заменяются обогащением.

## Разделение учёта и передачи (14.10.2026)

Ручные операции и сканер больше не вызывают API записи остатков маркетплейсов. Любая из двух складских кнопок атомарно применяет все C и D: сначала приходы, потом списания. При нехватке после прихода весь пакет отклоняется; F, история и оба поля остаются без изменений. Обработанные C/D очищаются в одной транзакции с журналом и складским запасом.

«Запустить трансляцию на МП» устанавливает сохраняемый флаг и регулярный облачный ntcTransmitterTick раз в5мин; первый вызов планируется разовым ntcTransmissionOnce. Кнопка сама не отправляет остатки синхронно. Закрытие вкладки/выключение Mac не влияет. «Остановить трансляцию» снимает только эти два обработчика. Выбор Ozon/WB остаётся отдельным: выключенная площадка не получает записи, её текущие значения не обнуляются. Флаг активной трансляции меняется после успешного создания триггеров. Ожидающее пересечение фоновых запусков пропускается без Telegram-ошибки и повторяется по расписанию.

Учёт ntcCloudTick раз в10мин продолжает работать независимо от трансляции. Это опрос с указанной задержкой, не мгновенный webhook/live. Из-за квоты личного Gmail (90мин времени триггеров/сутки) минутный цикл при измеренных временах небезопасен. События записываются в видимый лист «События FBS» атомарно с изменением F и журнала: площадка, заказ, статус до/после, артикул, модель, упаковки, кратность, учётное изменение в физических штуках, общий запас до/после цикла, комментарий и ID возврата. Учётное изменение не суммировать с агрегированными колонками до/после, которые повторены для событий модели в одном цикле. В Apps Script Logs события отражаются только после успешного коммита.

Старые отправления внесены как снимок с delta0 и пометкой «Учтён до включения журнала». Повторно они не списываются. Новые состояния/частичные количества/возвраты логируются как реальные изменения. Отмена до передачи восстанавливает запас; после подтверждённой или неизвестной передачи сохраняет списание до фактической приёмки. Ozon ReceivedBySeller восстанавливает только принятую часть и один раз по ID. WB неподтверждённая физическая приёмка — ручной приход. Нехватка, пропущенные между опросами статусы, повтор API, частичные возвраты, атомарность и UUID сохраняют прежние защиты.

## Актуальная схема после миграции 14.10.2026

Этот раздел заменяет исторические схемы колонок и расписания выше.

На «Склад НТЦ» три независимые таблицы с заголовками в строке 6: A:B — модель и физический запас; D:E — модель и поставка; G:H — модель и списание. Ввод начинается со строки 7. Порядок моделей в таблицах может различаться: движения сопоставляются по модели. Любая складская кнопка применяет оба списка атомарно, сначала поставки, затем списания. При дефиците весь пакет отклоняется. Первая таблица и каталог F меняются вместе; успешно обработанные количества E/H очищаются. Черновики сохраняются при обновлении карточек и форматировании.

Удалена прежняя H «Осаток распределение по артикулам». Теперь каталог: F — физический доступный запас модели; G «Виртуальный остаток» — дополнительный запас только для публикации; H «Х» — кратность; I — рассчитанная публикация; J — chrlid. Пользователь подтвердил смысл G: учёт заказов, поставок и списаний меняет только F. Пустая G равна 0; заполненная G должна быть целым неотрицательным числом. Формулы I используют F+N(G) перед распределением по упаковкам; G не списывается автоматически. Различные G в строках дают различные расчётные пулы публикации, даже у одной модели.

На панели J2:J10 девять кнопок, включая «АВТОТРАНСЛЯЦИЯ · ВКЛ / ВЫКЛ» (`ntcToggleAutoTransmission`). Она управляет тем же сохраняемым режимом, что запуск/остановка. Учёт FBS (`ntcCloudTick`) работает каждые 5 минут независимо. Активная трансляция (`ntcTransmitterTick`) также раз в 5 минут, продолжает работу после закрытия вкладки и отправляет только изменения/требующие согласования позиции включённых площадок. При выключенном режиме обработчик не читает каталог для поиска изменений и не публикует. Выключение не отменяет независимый учёт FBS.

Ozon отправления читаются через `/v4/posting/fbs/list`: statuses/warehouse_ids, cursor/sort_dir и top-level postings/has_next. Страница официальной документации: https://docs.ozon.ru/api/seller/#operation/PostingFbsList . Поле `delivering_date` означает дату передачи в доставку; `shipment_date` — срок сборки/рекомендуемое время передачи. `cancelled_after_ship` означает отмену после сборки, а не подтверждённую физическую передачу. Официально гарантированное автоматическое восстановление опубликованного доступного остатка при любой быстрой отмене не подтверждено.

Поэтому учёт восстанавливает списанные штуки один раз только при подтверждённой отмене до передачи; дата передачи и ранее увиденный статус доставки имеют приоритет и сохраняются в истории. При отмене после передачи или неизвестной передаче запас остаётся списанным до фактического `ReceivedBySeller`; частичные возвраты учитываются по принятому количеству и ID. Возврат на FBO не увеличивает НТЦ. Неоднозначный случай фиксируется в «События FBS» для складской сверки.

Каждое новое событие FBS помечает связанные артикулы для повторного согласования абсолютного остатка с МП. Это важно при отмене: цифровой резерв площадки мог измениться, даже если округлённое число упаковок в I осталось прежним. Метки сохраняются атомарно с журналом и снимаются только после успешной передачи соответствующей включённой площадке; повтор после сбоя безопасен.
