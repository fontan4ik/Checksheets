# НТЦ: локальная система списаний через F

## Единицы и колонки

- A — артикул продаваемой позиции.
- B — артикул производителя / модель; несколько строк могут использовать один физический запас.
- F — физические штуки модели **без кратности**. Для всех артикулов одной модели значение F должно быть одинаковым.
- G — справочное распределение, в расчёте первого этапа не участвует.
- H — кратность: физических штук в одной продаваемой единице.
- I — расчётное количество продаваемых единиц по артикулу для будущей передачи на маркетплейсы. Существующая формула читает F; локальный код её не меняет.
- J — `chrlid`; не участвует в списании.
- K — накопленное ручное списание в продаваемых единицах конкретного артикула: изменение с 2 на 3 при H=5 дополнительно вычитает 5 физических штук.
Дополнительные L, M и N удалены 17 сентября 2026 года. Текущий лист заканчивается на K. Перед удалением L её результаты совпадали с I во всех 21 строках; формулы I и L при этом не были текстуально одинаковыми.

## Что подключено сейчас

`ntc_live_local.py` работает на этом Mac через LaunchAgent `com.checksheets.ntc_live_local` раз в 60 секунд. Он локально читает Ozon FBS и возвраты, читает K из Google Sheet, пересчитывает F через журнал `logs/ntc_live_state.json` и записывает **только F**. I пересчитывается существующей формулой. Остатки на маркетплейсы скрипт не отправляет, Apps Script не запускает.

Первое включение 17 сентября 2026 года учло два отправления модели `1029089` с H=10: F модели `200 → 180`. Снимок до перехода сохранён в `logs/ntc_live_first_snapshot.json`; снимок перед удалением M/N — в `logs/ntc_before_column_cleanup.json`. Старый `ntc_fbs_reserve_sync.py --apply` отключён. Старый Apps Script остаётся в проекте, но локальная служба его не вызывает.

## Алгоритм активного первого этапа

1. Получить текущие F по моделям, список артикулов с H, обновлённые отправления Ozon, принятые возвраты и полный текущий снимок K.
2. Вести постоянный журнал по `posting_number` и ID возврата. Журнал хранит прошлые товары/количества, факт передачи отправления и уже применённое к F число физических штук. Пропущенное в очередном опросе отправление из журнала не удаляется.
3. При новом заказе на сборку учесть `количество × H` физических штук. Пример: заказ двух упаковок H=5 уменьшает F модели на 10.
4. При повторном опросе вычислить разницу между новым целевым списанием и ранее применённым. Если разница нулевая, F не меняется.
5. Если заказ отменён **до передачи**, обнулить его целевое списание и вернуть в F ранее вычтенные штуки. Частичное уменьшение количества до передачи возвращает только разницу.
6. Если заказ уже передавался, сохранить списание при отмене. Исторический признак передачи остаётся в журнале; текущий статус `cancelled` его не стирает. При пропуске промежуточного статуса используется поле Ozon `cancellation.cancelled_after_ship`. Если история передачи неизвестна, списание сохраняется для безопасности.
7. Для возвратов учитывать только FBS-записи Ozon со статусом `visual.status.sys_name = ReceivedBySeller`. По номеру отправления и артикулу вернуть в F `принятое количество × H`. Для частичного возврата вернуть только принятую часть. Один и тот же ID возврата применяется один раз; возврат сверх заказа останавливает расчёт с ошибкой.
8. K считать накопленным значением: новое целевое ручное списание равно `K × H`. При изменении K в F применяется только разница с предыдущим значением. При уменьшении/очистке K физические штуки возвращаются в F.
9. Для каждой модели вычислить `новое F = max(0; исходный физический запас модели − целевое списание)`. Если списание больше исходного запаса, F остаётся нулём, а нехватка хранится в журнале. Это позволяет при последующем уменьшении K или возврате восстановить ровно доступный запас. Состояние журнала и F должны сохраняться вместе, иначе повторный запуск может удвоить операцию.
10. В I ничего не записывать. Существующая формула читает изменённое F напрямую. Она распределяет общий запас модели и может оставить количество заказанного артикула неизменным; пользователь решил пока сохранить её для первого этапа. G и J в новом списании не используются.
11. Если F изменилась вне журнала между запусками, остановиться и потребовать сверку. Сейчас пользователь подтвердил, что исходные данные статичны. Когда складская синхронизация появится, нужно согласовать её изменения с журналом.

Все строки одной модели получают одинаковое новое F. В таблицу записываются только строки моделей, где F действительно изменился; после записи проверяются только эти ячейки F. Это не перезаписывает без необходимости F других моделей и сокращает пересчёт их зависимых формул I. Перед записью формируется локальный файл незавершённой операции; при сбое следующий запуск сравнивает F со старым и новым значениями и безопасно доводит запись до конца либо останавливается. Прямая передача I на маркетплейсы в этот этап не входит.

## Проверка

```bash
.venv-etm-export/bin/python test/test_ntc_f_stage.py -v
.venv-etm-export/bin/python test/test_ntc_live_local.py -v
.venv-etm-export/bin/python ntc_live_local.py
.venv-etm-export/bin/python test/test_ntc_f_stage_google.py
```

Проверка на рабочем листе: временное K=1 для H=5 изменило F `100→95`; после очистки K служба вернула F `95→100`. Тестовая запись K удалена. Проверка Google на временной вкладке отдельно протестировала `100→90→100→90→95` и удалила вкладку. Перед удалением L результаты I и L совпали во всех 21 строках; после удаления значения и формулы A:K совпали с сохранённым снимком `logs/ntc_before_i_only_cleanup.json`.

Ранее в K артикула `2851987-3` было введено 50. При H=3 это 150 физических штук против исходного F=100. Служба установила F=0 и сохранила нехватку 50. После очистки K значение F восстановилось до 100.

Состояние службы: `launchctl print gui/501/com.checksheets.ntc_live_local`. Журналы запуска: `logs/ntc_live_launchd.log` и `logs/ntc_live_launchd.err`. Ручной запуск без записи: `.venv-etm-export/bin/python ntc_live_local.py`; с записью: `.venv-etm-export/bin/python ntc_live_local.py --apply`.
