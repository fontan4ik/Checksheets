# НТЦ: текущая схема и первый этап прямого учёта F

## Единицы и колонки

- A — артикул продаваемой позиции.
- B — артикул производителя / модель; несколько строк могут использовать один физический запас.
- F — физические штуки модели **без кратности**. Для всех артикулов одной модели значение F должно быть одинаковым.
- G — справочное распределение, в расчёте первого этапа не участвует.
- H — кратность: физических штук в одной продаваемой единице.
- I — прежняя колонка округления и выгрузки; новым кодом не изменяется.
- J — `chrlid`; не участвует в списании.
- K — накопленное ручное списание в продаваемых единицах конкретного артикула: изменение с 2 на 3 при H=5 дополнительно вычитает 5 физических штук.
- L — расчётное количество продаваемых единиц по каждому артикулу для будущей передачи на маркетплейсы.
- M — в **нынешнем подключённом варианте** резерв FBS в физических штуках по модели.
- N — в **нынешнем подключённом варианте** `F − M − Σ(K × H)` по модели.

## Что подключено сейчас

Лист «НТЦ списания» уже содержит формулы L/N и проверку ввода K. Локальный `ntc_fbs_reserve_sync.py` читает Ozon и по умолчанию показывает расчёт без записи. Его явный `--apply` обновляет M и скрытый журнал отправлений. Автоматический локальный запуск выключен. Текущий Apps Script также может делать ручную сверку. В этой подключённой схеме F не меняется, а M/N уменьшают доступный запас; её L перераспределяет модельный запас и не гарантирует уменьшение L именно заказанного артикула.

**Новый первый этап пока отдельный.** `ntc_f_stage.py` не читает и не меняет Google Sheet. Он рассчитывает, какие значения надо записать в F и L после события. При будущем подключении старый вычет через M/N нужно выключить или изменить: если уменьшить F и одновременно вычесть тот же заказ через M, возникнет двойное списание.

## Алгоритм отдельного первого этапа

1. Получить текущие F по моделям, список артикулов с H, обновлённые отправления Ozon, принятые возвраты и полный текущий снимок K.
2. Вести постоянный журнал по `posting_number` и ID возврата. Журнал хранит прошлые товары/количества, факт передачи отправления и уже применённое к F число физических штук. Пропущенное в очередном опросе отправление из журнала не удаляется.
3. При новом заказе на сборку учесть `количество × H` физических штук. Пример: заказ двух упаковок H=5 уменьшает F модели на 10.
4. При повторном опросе вычислить разницу между новым целевым списанием и ранее применённым. Если разница нулевая, F не меняется.
5. Если заказ отменён **до передачи**, обнулить его целевое списание и вернуть в F ранее вычтенные штуки. Частичное уменьшение количества до передачи возвращает только разницу.
6. Если заказ уже передавался, сохранить списание при отмене. Исторический признак передачи остаётся в журнале; текущий статус `cancelled` его не стирает. Если история передачи неизвестна, списание сохраняется для безопасности.
7. Для возвратов учитывать только FBS-записи Ozon со статусом `visual.status.sys_name = ReceivedBySeller`. По номеру отправления и артикулу вернуть в F `принятое количество × H`. Для частичного возврата вернуть только принятую часть. Один и тот же ID возврата применяется один раз; возврат сверх заказа останавливает расчёт с ошибкой.
8. K считать накопленным значением: новое целевое ручное списание равно `K × H`. При изменении K в F применяется только разница с предыдущим значением. При уменьшении/очистке K физические штуки возвращаются в F.
9. Для каждой модели вычислить `новое F = текущее F − (новое целевое списание − уже применённое списание)`. Отрицательный результат блокируется. Состояние журнала и F должны сохраняться вместе, иначе повторный запуск может удвоить операцию.
10. L рассчитывать по артикулу в продаваемых единицах: снизить лимит именно заказанного артикула и артикула с K, затем проверить `Σ(L × H) ≤ F`. G, I и J не используются.
11. Если F изменилась вне журнала между запусками, остановиться и потребовать сверку. Сейчас пользователь подтвердил, что исходные данные статичны. Когда складская синхронизация появится, нужно согласовать её изменения с журналом, прежде чем включать автоматическую работу.

Для будущего подключения к таблице все строки одной модели должны получить одинаковое новое F. Запись F, L и журнала должна быть согласованной; запись только части результатов недопустима. Прямая передача L на маркетплейсы в этот этап не входит.

## Проверка

```bash
.venv-etm-export/bin/python test/test_ntc_f_stage.py -v
.venv-etm-export/bin/python ntc_f_stage.py --input test/ntc_stock_example.json
.venv-etm-export/bin/python test/test_ntc_f_stage_google.py
```

Локальный пример: F=100, заказ одной упаковки H=10 и K=2 при H=5 дают F=80. L заказанного артикула H=10 снижается с 5 до 4, а H=5 — с 6 до 4. Проверка Google создаёт временную вкладку, тестирует `100→90→100→90→95` и удаляет её. Рабочий лист не меняется.
