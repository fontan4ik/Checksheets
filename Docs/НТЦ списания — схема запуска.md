# НТЦ списания

## Расчёт

- F — входной физический остаток модели. Скрипт никогда не записывает в F.
- K — **накопленное** ручное списание в упаковках данного артикула. Например, `2` для кратности H=`5` означает вычет 10 физических штук из общего запаса модели. Редактирование `2` на `3` увеличивает вычет ещё на одну упаковку; очистка возвращает этот ручной вычет. Формулы пересчитываются сразу, отдельный триггер для ручного ввода не нужен. J содержит `chrlid` и не участвует в вычете.
- L — итоговое количество упаковок артикула для будущей выгрузки на маркетплейсы. Оно распределяется между кратностями одной модели так, чтобы общие физические штуки не обещались несколько раз. Дубли одинаковой кратности внутри модели получают 0 до исправления данных.
- M — резерв Ozon FBS в физических штуках модели, одинаковый для всех строк модели.
- N = F − M − сумма(K × H) по всем артикулам модели. Отрицательное N показывает превышение доступного запаса.
- G — справочная колонка. I и API остатки Ozon/WB не изменяются.

## Заказы

`installNtcWriteOffs()` создаёт скрытый журнал по `posting_number`, записывает формулы L/N и выполняет первую сверку. Отдельный Apps Script-триггер не создаётся: в проекте достигнут лимит триггеров. Локальный `ntc_fbs_reserve_sync.py` повторно читает активные и изменённые отправления. Повторное чтение не удваивает резерв и ловит частичную отмену без смены статуса.

Отмена до передачи в доставку освобождает резерв. Если отправление уже передавалось в доставку, статус отмены сам по себе не подтверждает физический возврат, поэтому резерв сохраняется до отдельного учёта фактически принятого возврата. Ошибка API или неизвестный формат не заменяет предыдущий резерв нулями. Заказы других артикулов того же склада игнорируются.

## Перед включением

Нужно подтвердить, содержит ли будущий источник F уже списания по FBS и ручные списания. Если содержит, постоянный вычет из F даст двойное списание; тогда алгоритм нужно переключить на временный резерв до отражения операции в F. Текущие формулы рассчитаны на F как на исходный запас **до** этих списаний.

Лист Google уже подготовлен: K имеет проверку ввода, M содержит предварительный резерв, L/N содержат формулы. Автоматический локальный запуск пока выключен. Для теста без записи: `.venv-etm-export/bin/python ntc_fbs_reserve_sync.py`; для явного обновления M: `.venv-etm-export/bin/python ntc_fbs_reserve_sync.py --apply`. Шаблон будущего минутного LaunchAgent находится в `scripts/com.checksheets.ntc_fbs_reserve.plist` и сейчас не установлен.

Даже после включения L доступный остаток уменьшается только внутри таблицы. Остатки маркетплейсов останутся прежними, поэтому исключить новые сверхзаказы через маркетплейсы до подключения отдельной безопасной выгрузки невозможно.

## Проверки

`node test/test_ntc_write_offs.js` и `.venv-etm-export/bin/python test/test_ntc_fbs_reserve_sync.py` — повторный опрос, отмена до/после отправки, посторонние артикулы, ошибки API, некорректные данные и проверка, что ручное списание читается из K, а не из J. Реальные запросы Ozon `/v2/warehouse/list` и `/v3/posting/fbs/list` выполнены только на чтение; фильтры статуса и `last_changed_status_date` вернули HTTP 200. Формулы L/N проверены в отдельном временном листе Google Sheets: при F=100, резерве M=3 и K=1 для H=5 колонка N дала 92, а L распределила 90 физических штук без превышения доступного запаса. Временный лист удалён.
